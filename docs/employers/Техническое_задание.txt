Техническое задание на модуль сотрудников Equipment Rental

1. Общие сведения
Разрабатывается модуль employers для учёта сотрудников организации, сдающей ПК, мониторы и периферию компьютерным клубам. Репозиторий: Interlink-Labs/equipment_rental. Ответственная часть проекта — сотрудники. Этап разработки — учебная доработка существующей серверной части на Python.

2. Назначение и цели разработки
Модуль предназначен для централизованного хранения карточек сотрудников. Цель — исключить повторяющиеся логины, обеспечить управляемое изменение данных и быстрый поиск. Результат — API, связанный с общей авторизацией и документированный в OpenAPI.

3. Описание объекта автоматизации
Сотрудник представлен полями id, username, full_name, role и is_active. Роли карточки: MANAGER и ADMIN; состояния: ACTIVE и BLOCKED. Таблица employers существует отдельно от auth_users. Изменение роли или блокировка карточки не изменяет учётную запись входа и её JWT-права. Привязка карточки сотрудника к аккаунту не входит в текущую доработку.

4. Требования к системе
4.1. Функциональные требования
F1. Создавать карточку сотрудника с ФИО, уникальным логином и ролью; по умолчанию MANAGER и ACTIVE.
F2. Возвращать список сотрудников и отдельную карточку по ID.
F3. Изменять ФИО и роль; логин сохранять неизменным.
F4. Устанавливать состояние карточки ACTIVE или BLOCKED.
F5. Удалять только карточку в состоянии BLOCKED; активную карточку предварительно блокировать.
F6. Искать по ФИО и логину без учёта регистра, фильтровать по роли и состоянию.
F7. Сортировать по id, username или full_name в направлениях asc и desc.
F8. Проверять JWT и роль ADMIN через существующий require_admin для всех маршрутов employers.

4.2. Нефункциональные требования
Производительность. На учебном наборе до 1000 карточек целевое время ответа — до 1 с на локальном сервере. Это требование к приёмке; 30 функциональных проверок не заменяют нагрузочные испытания. Текущий поиск выполняется в памяти после чтения записей, поэтому для большого объёма требуется отдельная оптимизация.
Надёжность. Изменения сохраняются транзакционно; при конфликте уникального логина выполняется откат. Ошибки входных данных не должны изменять базу.
Безопасность. Все эндпоинты доступны только ADMIN по Authorization: Bearer <JWT>. Токен не передаётся в URL. Используется общая авторизация проекта; повторная система паролей для карточек сотрудников не создаётся.
Удобство использования. Поля и ответы описаны в Swagger /docs; возвращаются понятные сообщения и коды ошибок. Пустое ФИО и неподдерживаемые роли отклоняются.
Совместимость и эксплуатация. Python 3.10+, FastAPI, Pydantic 2, SQLAlchemy 2, SQLite, JSON через HTTP; версии устанавливаются из requirements.txt. Для проверок дополнительно нужен httpx. При обновлении не меняются контракты модулей остальных пар.

5. Состав и содержание работ
Анализ существующих моделей → декомпозиция требований → схема backend → контракты входных и выходных данных → реализация маршрутов и валидации → проверка CRUD, JWT, поиска и сортировки → код-ревью и слияние → оформление отчёта.
Файлы реализации: routers/employers.py, employers_schemas.py. Проверки: tests/check_employers.py. Общие auth.py, database.py, models.py и main.py используются без изменений.

6. Порядок контроля и приёмки
Проверить создание, чтение, изменение, блокировку и удаление карточки. Проверить поиск по ФИО и логину, фильтры и обратный порядок сортировки. Неверный JWT даёт 401, роль USER — 403, отсутствующий ID — 404, конфликт — 409, неверные поля — 422. Принять модуль после успешного прохождения автоматических проверок, просмотра OpenAPI и согласования изменений с командой. Время ответа проверяется отдельно на согласованном стенде.
